# AI智能告警诊断系统面试深挖文档

## 1. 项目一句话概述

本项目是一个基于 LangGraph、飞书机器人、Milvus 向量数据库和 RAG 技术构建的 AIOps 智能告警诊断系统，目标是将传统依赖人工经验的告警排查流程，升级为可编排、可解释、可复用、可反馈学习的智能诊断闭环。

系统覆盖以下核心流程：

```text
告警接入
  -> 告警理解
  -> 历史案例缓存查找
  -> RAG 知识检索
  -> 实时工具调用
  -> 诊断方案生成
  -> 方案校验
  -> 人机确认
  -> 结果反馈入库
```

如果从面试官角度评价，该项目的重点不只是“接了一个大模型”，而是围绕生产故障诊断场景，解决了以下工程问题：

- 如何把不稳定的大模型能力放进可控工作流。
- 如何把静态知识和历史经验统一检索。
- 如何避免错误答案污染知识库。
- 如何在群聊场景中保持交互清晰。
- 如何让一次诊断结果沉淀为下一次可复用资产。

## 2. 项目总结（面试表达版）

主要工作：独立设计并实现基于 LangGraph、飞书机器人与 Milvus 向量数据库的 AI 智能告警诊断系统，构建从告警理解、RAG 检索、实时工具调用、方案生成、方案校验、人机确认到反馈学习的闭环诊断链路。

- 针对传统人工排障依赖个人经验、响应链路长、重复故障处理效率低的问题，通过 LangGraph 编排多节点诊断流程，将告警理解、知识检索、工具调用、方案生成和人工确认标准化，实现告警诊断流程从人工驱动向自动化辅助决策转变。
- 针对大模型直接输出诊断方案存在幻觉和高风险操作不可控的问题，设计结构化 JSON 输出、危险操作规则拦截和 LLM 二次校验机制，将方案生成与方案审核拆分为独立节点，提升诊断结果的可控性。
- 针对故障手册长文档检索粒度粗、上下文噪声高的问题，基于 Markdown 标题层级进行语义切片，并提取章节、故障类型、严重等级、错误码和关键词等元数据，使 RAG 检索结果更贴合运维排障场景。
- 针对历史成功案例难复用的问题，构建 `aiops_message_history` 历史案例向量库，在告警理解阶段优先进行相似案例缓存查找，命中高相似案例后通过飞书卡片让用户一键采用，减少重复诊断成本。
- 针对 RAG 检索中历史案例容易被静态文档挤掉的问题，将交互式 RAG 展示拆分为“文档/混合召回 Top2”和“历史案例召回 Top2”，保证标准知识和真实案例都能被用户看到。
- 针对 AI 诊断结果难以持续沉淀的问题，设计“有效，存入知识库 / 无效，不存储”的反馈学习机制，仅将用户确认有效的诊断过程写入 Milvus，避免错误答案污染历史案例库。
- 针对飞书群聊中多节点消息刷屏的问题，将原有多消息模式改造为单张飞书交互卡片动态更新，通过状态图标展示节点进度、当前节点结果和操作按钮，提升协同排障体验。
- 针对 Milvus 中文字段长度按字节限制导致入库失败的问题，实现 UTF-8 字节级安全截断，并在入库失败后恢复反馈状态，支持用户重试或选择不存储，提升系统鲁棒性。

## 3. 总体架构深挖

### 3.1 架构分层

系统可以拆成六层：

```text
接入层：飞书事件 / HTTP 告警接口
交互层：飞书单卡片动态更新 / 按钮回调
编排层：LangGraph 工作流
智能层：LLM 告警理解、方案生成、方案校验
知识层：Milvus 静态文档库 + 历史案例库
工具层：指标、日志、拓扑等实时数据源
```

这种分层的好处是，每一层职责清晰：

- 接入层只关心事件进入。
- 编排层只关心状态流转。
- 知识层只关心召回。
- 工具层只关心现场数据。
- 智能层只关心推理生成。
- 交互层只关心人机协同。

面试中如果被问“为什么不直接用一个接口调大模型返回答案”，可以这样回答：

> 因为告警诊断不是普通问答，而是一个具有状态、证据、校验、人机确认和反馈沉淀的流程型任务。单次 LLM 调用无法稳定承载检索、工具调用、方案校验和用户反馈闭环，也不利于定位故障是发生在检索、工具还是生成阶段。

## 4. 文档切分策略深挖

### 4.1 为什么需要文档切分？

故障手册通常是长 Markdown 文档，可能包含多个章节：

```text
# 第一章 消息队列故障
## 1.1 消息堆积
### 1. 消费能力不足
### 2. 消费逻辑阻塞

# 第二章 应用服务故障
## 2.1 P95/P99 延迟飙升
```

如果直接把整篇文档作为一个向量写入数据库，会出现三个问题：

1. 向量表达过于平均  
   一篇长文档包含 MQ、Redis、MySQL、JVM 等多个主题，整体 embedding 会被稀释，无法准确表示某个具体故障场景。

2. 检索结果上下文过长  
   即使命中，也会返回大量无关内容，增加 LLM 输入噪声和 token 成本。

3. 无法做细粒度元数据过滤  
   如果不切片，就很难知道某段内容属于哪个章节、哪个故障类型、哪个严重等级。

因此，RAG 系统中必须先进行文档切分。

### 4.2 为什么选择 MarkdownHeaderTextSplitter？

本项目使用：

```python
MarkdownHeaderTextSplitter(
    headers_to_split_on=[
        ("#", "h1"),
        ("##", "h2"),
        ("###", "h3"),
    ]
)
```

原因是故障手册本身具有清晰的 Markdown 标题结构。标题通常天然表达语义边界：

- 一级标题：大类故障，如消息队列、JVM、Redis。
- 二级标题：具体故障场景，如消息堆积、Full GC。
- 三级标题：原因分类或排查步骤，如消费能力不足、锁竞争。

用标题切分比固定长度切分更适合运维手册，因为它保留了人类编写文档时的知识结构。

### 4.3 与其他切分方法对比

| 切分方法 | 原理 | 优势 | 问题 | 是否适合本项目 |
| --- | --- | --- | --- | --- |
| 固定字符切分 | 每 N 个字符切一段 | 实现简单，适合无结构文本 | 容易切断语义，标题和正文分离 | 不优先 |
| Token 切分 | 按模型 token 数切分 | 能控制 LLM 上下文长度 | 不理解文档结构 | 可作为二次切分补充 |
| 递归字符切分 | 按段落、句子、字符递归切 | 通用性强 | 对 Markdown 层级利用不足 | 可用于无标题文档 |
| Markdown 标题切分 | 按标题层级切分 | 保留章节语义和元数据 | 依赖文档标题规范 | 最适合本项目 |
| 语义切分 | 根据 embedding 相似度找语义边界 | 语义更智能 | 成本高、实现复杂、可解释性弱 | 后续可探索 |

本项目选择 Markdown 标题切分，是因为故障手册是结构化 Markdown，标题本身就是最稳定、可解释、低成本的语义边界。

### 4.4 切片元数据为什么重要？

每个切片不仅保存正文，还会补充：

```text
doc_id
section
alert_category
severity_level
error_code
keywords
last_updated
```

这些元数据的作用包括：

- 展示时告诉用户命中的是哪个章节。
- 后续可按告警类别过滤，例如只查 Redis 或 MySQL。
- 可用于 rerank，例如 P0 故障优先。
- 可用于评估知识覆盖情况。
- 可用于审计和追溯文档来源。

如果只有 embedding，没有元数据，RAG 系统会变成一个黑盒，命中了什么内容、来自哪里、是否适合当前场景都不清楚。

## 5. RAG 检索算法深挖

### 5.1 当前检索链路

系统当前有两类知识源：

```text
静态文档库 aiops_static_docs
历史案例库 aiops_message_history
```

检索流程：

```text
用户告警文本
  -> Embedding 模型生成向量
  -> Milvus COSINE 相似度检索
  -> 静态文档 TopK
  -> 历史案例 TopK
  -> 加权合并
  -> MMR 去冗余
  -> 输出最终上下文
```

### 5.2 为什么使用向量相似度检索？

告警文本通常是自然语言描述，不一定包含和文档完全一致的关键词。例如：

```text
用户告警：订单同步变慢，队列堆积上涨
文档标题：消息大规模堆积故障
```

全文检索可能因为关键词不完全一致而召回不足，但向量检索可以捕捉“同步变慢”“队列堆积”和“消息堆积故障”之间的语义相似性。

### 5.3 为什么使用 COSINE 相似度？

Milvus 向量检索可选多种距离方式：

- COSINE
- L2
- IP

本项目选择 COSINE，原因是文本 embedding 更关注方向相似度，而不是向量绝对长度。COSINE 衡量两个向量夹角，更适合语义相似度判断。

对比：

| 相似度算法 | 特点 | 适用场景 |
| --- | --- | --- |
| COSINE | 关注方向，不受向量模长影响 | 文本语义检索 |
| L2 | 计算欧氏距离，受向量尺度影响 | 图像、数值特征更常见 |
| IP | 内积相似度，适合归一化向量或推荐场景 | 推荐召回、归一化 embedding |

文本 RAG 中，COSINE 是更常见和稳定的默认选择。

### 5.4 为什么使用 MMR？

如果只按相似度 TopK 返回，很容易出现多个高度重复的片段。例如：

```text
Top1：消息堆积排查 SOP
Top2：消息堆积根因分析
Top3：消息堆积消费者扩容方案
```

这些结果可能都围绕同一小点，缺少多样性。MMR（Maximal Marginal Relevance）会在“相关性”和“多样性”之间平衡。

MMR 的基本思想：

```text
score = λ * relevance(query, doc) - (1 - λ) * similarity(doc, selected_docs)
```

其中：

- `relevance` 表示文档和查询是否相关。
- `similarity(doc, selected_docs)` 表示该文档和已选文档是否重复。
- `λ` 控制相关性和多样性的权重。

本项目默认：

```env
RAG_MMR_LAMBDA=0.55
```

说明系统略微偏向相关性，同时保留一定去冗余能力。

### 5.5 MMR 与普通 TopK 对比

| 方法 | 优势 | 问题 |
| --- | --- | --- |
| 相似度 TopK | 简单直接，召回最相似内容 | 结果容易重复 |
| MMR | 兼顾相关性和多样性 | 需要额外计算文档间相似度 |
| Rerank 模型 | 排序效果更强 | 增加模型成本和延迟 |
| 规则排序 | 可解释、可控 | 难覆盖复杂语义 |

当前项目使用 MMR，是工程上性价比较高的方案。后续如果有更多数据，可以加入 rerank 模型或基于字段的加权排序。

### 5.6 为什么 RAG 检索要分开展示静态文档和历史案例？

系统最初将静态文档和历史案例混合后做 MMR Top2。这样可能出现一个问题：

```text
Top2 都是静态文档
历史案例虽然命中，但没有展示
```

用户会误以为“缓存查找能命中，但 RAG 检索不能命中”。

因此交互式 RAG 卡片改为：

```text
文档/混合召回 Top2
历史案例召回 Top2
```

这样做的优势是：

- 静态标准知识和历史真实案例都可见。
- 用户能理解 AI 诊断依据来自哪里。
- 避免历史案例被静态文档挤掉。
- 便于后续评估两类知识源的贡献。

## 6. 历史案例缓存机制深挖

### 6.1 缓存查找解决什么问题？

大量线上告警具有重复性。例如：

- 同一个服务的连接池耗尽。
- 同一个 Topic 的消息堆积。
- 同一个 Redis 热 Key。
- 同一个接口 P99 延迟飙升。

如果每次都完整执行 RAG、工具调用和 LLM 生成，会带来：

- 响应慢。
- 成本高。
- 结果不稳定。
- 历史经验无法复用。

因此系统在告警理解阶段先查历史成功案例。

### 6.2 为什么阈值默认 0.85？

历史案例复用比普通 RAG 更敏感。普通 RAG 只是给 LLM 提供参考，而缓存复用可能直接跳过后续节点并采用历史方案。

因此相似度阈值不能太低。

阈值设计考虑：

| 阈值 | 影响 |
| --- | --- |
| 过低，例如 0.6 | 容易误用不相关历史方案 |
| 过高，例如 0.95 | 命中率低，复用价值下降 |
| 0.85 左右 | 在召回率和误判率之间较平衡 |

默认 `0.85` 是一个保守起点，后续应结合生产数据调整。

### 6.3 为什么命中后还要用户确认？

因为历史案例即使相似，也不一定完全适用。比如两个告警都叫“CPU 飙升”，但根因可能不同：

- 一次是 Full GC。
- 一次是死循环。
- 一次是流量突增。
- 一次是线程池阻塞。

如果系统自动采用历史方案，可能导致误导。因此设计为：

```text
命中历史案例 -> 飞书卡片展示 -> 用户选择采用 / 不采用
```

这是在效率和安全之间的折中。

### 6.4 为什么只把用户确认有效的结果入库？

如果所有 AI 输出都自动入库，会产生“错误知识污染”：

```text
错误诊断 -> 自动入库 -> 后续相似告警召回错误案例 -> 继续错误
```

所以系统通过用户反馈做质量门禁：

- 有效，存入知识库。
- 无效，不存储。

这使历史案例库更接近“人工确认过的成功经验”，而不是“模型生成过的所有内容”。

## 7. LangGraph 工作流设计深挖

### 7.1 为什么工作流要有条件边？

告警诊断不是固定线性流程。例如：

- 缓存命中可直接结束。
- 低风险告警可能不需要实时工具。
- 校验失败需要重新生成方案。
- 人工拒绝需要带反馈回到生成节点。

LangGraph 条件边可以清晰表达这些路径。

示例：

```text
understand
  -> cache hit -> final_result
  -> cache miss -> retrieve

validate
  -> pass -> human_confirm
  -> fail -> generate_plan
```

如果用普通脚本实现，这些条件会散落在大量 `if/else` 中，不利于维护。

### 7.2 为什么要支持节点失败跳过？

生产系统里外部依赖不稳定，例如：

- 工具接口超时。
- RAG 服务异常。
- LLM 调用失败。
- 飞书卡片更新失败。

如果任一节点失败就终止整个流程，系统可用性会很差。因此交互式流程支持：

```text
失败或重试 2 次以上 -> 跳过当前节点 -> 继续下一节点
```

这种设计优先保证系统能给出可用结果，同时在卡片中明确标记节点已跳过。

## 8. 飞书交互卡片设计深挖

### 8.1 为什么从多消息改为单卡片？

初始设计中，每个节点可能发送多条消息：

- 开始执行消息。
- 节点结果文本。
- 确认卡片。

节点多了以后，群聊会出现刷屏，用户很难知道当前流程走到哪一步。

单卡片设计把所有信息收敛到一张卡片：

- 步骤列表。
- 状态图标。
- 当前节点结果。
- 按钮操作。
- 最终反馈。

这样更适合群聊协同场景。

### 8.2 为什么需要更新锁？

飞书卡片更新是异步操作，节点执行、用户点击、超时回调可能并发发生。如果多个更新同时 PATCH 同一张卡片，可能出现：

- 后发先至导致状态回退。
- 卡片内容闪烁。
- 用户看到错误按钮。

因此系统为每个 message_id 维护异步锁，保证同一张卡片同一时刻只有一个更新操作。

### 8.3 为什么按钮回调要可恢复工作流？

人机确认本质是一个中断点。工作流执行到卡片按钮处暂停，等待用户点击后继续。

如果没有恢复机制，就只能把“点击按钮”写成普通 HTTP 回调，难以回到原来的诊断状态。

LangGraph interrupt/resume 能保留上下文，使用户点击后继续从当前节点往下执行。

## 9. Milvus 入库健壮性深挖

### 9.1 为什么会出现 VARCHAR 超长？

Milvus schema 中：

```text
title: VARCHAR(512)
metadata: VARCHAR(8192)
```

需要注意，Milvus 的长度限制按字节计算，而中文通常一个字符占 3 个 UTF-8 字节。

如果用 Python 的 `text[:512]` 截断，只是截断 512 个字符，实际可能超过 1536 字节。

### 9.2 为什么要做 UTF-8 字节级截断？

为了严格符合 Milvus 字段限制，需要按字节截断：

```python
data = value.encode("utf-8")
data[:max_bytes].decode("utf-8", errors="ignore")
```

这样既不会超过字段最大字节数，也不会产生非法 UTF-8 字符。

### 9.3 为什么入库失败后要恢复反馈状态？

如果用户点击“有效，存入知识库”后入库失败，而系统已经把任务状态标记为 `feedback_received`，后续用户再点击按钮会被认为是重复操作。

因此修复为：

```text
入库失败
  -> 记录错误
  -> 恢复 pending_feedback
  -> 卡片重新显示反馈按钮
```

这样用户可以重试，也可以选择“不存储”结束流程。

## 10. 面试高频追问与推荐回答

### 10.1 如果面试官问：你的 RAG 和普通知识库问答有什么区别？

推荐回答：

> 普通知识库问答通常只做 query 到 document 的相似度检索，然后让 LLM 回答。本项目的 RAG 是嵌入在 AIOps 工作流里的，不仅检索静态文档，还检索历史成功案例，并且检索结果会参与后续工具调用、方案生成、校验和人机确认。历史案例还可以通过用户反馈持续写回向量库，形成闭环。

### 10.2 如果面试官问：为什么不直接用 ES？

推荐回答：

> ES 更擅长关键词和结构化字段检索，例如错误码、服务名、日志关键字。但告警诊断中大量输入是自然语言描述，表达方式和文档不完全一致，因此需要向量检索捕捉语义相似性。后续最理想的方案是 ES/BM25 + Milvus 向量的混合检索。

### 10.3 如果面试官问：为什么需要 MMR？

推荐回答：

> 单纯 TopK 相似度容易返回多个重复片段，尤其故障手册中相近章节很多。MMR 可以在相关性和多样性之间做平衡，避免上下文都集中在同一类内容上，从而给 LLM 更全面的证据。

### 10.4 如果面试官问：历史案例会不会越积越乱？

推荐回答：

> 所以系统没有自动入库所有回答，而是通过用户反馈做质量门禁。只有用户点击“有效，存入知识库”后才写入历史案例库。同时 metadata 中保存完整诊断过程，后续可以按服务、组件、标签、时间和反馈质量做清理或重排。

### 10.5 如果面试官问：这个系统如何防止危险操作？

推荐回答：

> 系统把方案生成和方案校验拆成两个节点。校验节点包含规则拦截和 LLM 二次判断，规则层会过滤高危命令或删除类操作，LLM 层再从语义上判断方案是否合理。高风险场景还需要飞书人机确认，不会直接自动执行。

### 10.6 如果面试官问：为什么选择 LangGraph？

推荐回答：

> 因为告警诊断是典型的多步骤、有状态、可中断、可回退流程。LangGraph 可以用节点和条件边表达诊断路径，支持 interrupt/resume 处理人工确认，比纯 LangChain Chain 更适合复杂工作流，也比自定义状态机更省维护成本。

## 11. 可量化指标设计

如果后续需要向面试官展示效果，可以补充以下指标：

| 指标 | 含义 |
| --- | --- |
| 历史案例缓存命中率 | 相似告警中能命中历史案例的比例 |
| 历史案例采纳率 | 用户点击“采用此方案”的比例 |
| 有效入库率 | 用户确认诊断有效并入库的比例 |
| 平均诊断耗时 | 从告警进入到输出方案的时间 |
| LLM 调用次数下降 | 缓存命中后跳过后续节点带来的成本下降 |
| 人工介入率下降 | AI 可直接给出可采纳建议的比例提升 |
| 方案校验拦截率 | 高风险或不合格方案被拦截的比例 |

当前工程侧已有：

- 默认静态文档 Top2。
- 默认历史案例 Top2。
- 缓存相似度阈值 0.85。
- 节点失败或重试 2 次后跳过。
- 单卡片动态更新。
- 34 个自动化测试用例通过。

## 12. 后续优化方向

### 12.1 引入混合检索

将 Milvus 向量检索与 BM25/ES 关键词检索结合，提升错误码、日志关键字、服务名等精确匹配能力。

### 12.2 引入 Cross-Encoder Rerank

当前 MMR 主要解决多样性问题，后续可以用 rerank 模型对 TopN 结果做更精细排序，提升最终上下文质量。

### 12.3 增强历史案例评分

历史案例排序可以从单一向量相似度升级为多因子评分：

```text
最终分 = 向量相似度 * w1
      + 服务匹配分 * w2
      + 组件匹配分 * w3
      + 标签重合分 * w4
      + 时间衰减分 * w5
      + 用户反馈质量分 * w6
```

### 12.4 接入真实监控工具

后续可以接入：

- Prometheus
- Loki
- OpenSearch
- Kubernetes API
- CMDB
- 发布系统
- 链路追踪系统

### 12.5 建设离线评测集

收集历史告警、标准根因、标准方案和禁用操作，构建回放评测体系，用于量化：

- 检索准确率。
- 根因判断准确率。
- 方案可采纳率。
- 危险操作拦截率。
- Token 成本。

## 13. 总结

这个项目的核心价值在于，它不是简单地把大模型接到告警群里，而是围绕真实 AIOps 场景构建了一套可控的智能诊断闭环：

- 用 LangGraph 保证流程可编排。
- 用 RAG 保证回答有知识依据。
- 用工具调用补充实时现场数据。
- 用方案校验降低高风险输出。
- 用飞书卡片实现人机协同。
- 用反馈学习沉淀历史经验。
- 用 Milvus 向量库支撑语义检索和缓存复用。

从面试表达角度，这个项目可以重点突出三个能力：

1. 对复杂 LLM 应用工程化落地的理解。
2. 对 RAG 检索、文档切分、向量数据库和反馈闭环的掌握。
3. 对生产级交互、异常恢复和系统鲁棒性的设计能力。
