# AI 告警助手优化后实现：简历亮点 8 条版

## 可直接写进简历的版本

主要工作：参与自研 AI 智能告警助手（Agent Sentinel / Seatalk-bot）的优化迭代，将原先“拉取消息 -> Milvus 历史消息相似检索 -> 拼接历史回复调用 LLM”的线性问答链路，升级为基于 LangGraph、多 Agent、Hybrid RAG、历史案例缓存和反馈学习的智能告警诊断系统，驱动回答准确性、处理成本、流程可控性和知识沉淀能力的系统化提升。

- 针对旧版告警助手依赖单次 LLM 调用、流程不可观测、失败后难以局部重试的问题，通过 LangGraph 将告警理解、RAG 检索、实时数据获取、方案生成、安全校验、人工确认、最终总结、反馈学习拆分为可配置节点，并基于 `workflow.yaml` 编排条件路由，实现诊断流程从线性问答升级为可追踪、可恢复、可干预的多阶段工作流。

- 针对复杂告警处理中模型职责混杂、Prompt 难以维护、诊断证据无法沉淀的问题，通过设计 Understand、Retrieve、Tool Fetch、Plan Generate、Validate、Human Confirm、Feedback Learning 等专职 Agent 节点，统一使用 `DiagnosisState` 传递告警摘要、检索上下文、实时数据、推荐方案和证据链，实现“理解-检索-推理-校验-反馈”的解耦协同，提高复杂流程下的扩展性和可控性。

- 针对旧版仅检索历史消息导致标准 SOP 缺失、上下文噪声高的问题，通过构建静态知识文档索引流程，基于 Markdown 标题层级切片故障手册，自动抽取 `section`、`alert_category`、`severity_level`、`error_code`、`keywords`、`source_uri` 等元数据，并批量向量化写入 Milvus，实现故障预案、Runbook、FAQ 等稳定知识的结构化召回。

- 针对单一路径向量检索容易召回重复历史回复、Prompt 被低价值上下文占满的问题，通过搭建“静态文档库 + 历史成功案例库”的双路 Hybrid RAG 架构，结合服务级过滤、时间窗口过滤、来源权重、近期案例加权和 MMR 去冗余策略，实现从“相似历史回复”升级为“标准预案 + 近期实战案例”的高相关、多样化上下文选择。

- 针对重复告警频繁走完整 LLM 诊断链路、响应慢且 token 成本高的问题，通过在告警理解阶段引入历史成功案例缓存，按相似度阈值召回 `alert_case`，并通过飞书卡片让值班人员确认是否采用历史方案；命中并确认后可直接跳过 RAG、工具调用和方案生成，实现重复告警的快速复用与成本降低。

- 针对历史案例自动复用存在误判风险、AI 结果直接入库容易污染知识库的问题，通过设计反馈学习闭环，在最终结果后由飞书卡片收集“有效/无效”反馈，仅将人工确认有效的告警原文、RAG 结果、实时数据、推荐方案、证据链和工作流日志写入 Milvus，实现历史案例库从被动检索升级为可控自进化的长期记忆。

- 针对 LLM 输出格式不稳定、自动化建议可能包含高危操作的问题，通过统一 `LLMExecutor` 封装多模型降级、超时控制、指数退避重试和 Mock 模式，结合 Pydantic 结构化输出解析、危险命令规则拦截与 LLM 二次校验，实现诊断方案生成的稳定性、安全边界和工程可测试性提升。

- 针对告警处理链路中指标、日志、拓扑等外部数据串行调用耗时高，以及飞书群内多消息刷屏的问题，通过异步并发工具调用和交互式单卡片工作流，持续更新节点状态、支持同意/拒绝/超时自动继续/最多重试 2 次，实现端到端处理效率、用户可见性和人工介入体验的同步优化。

> 简历中如果要写量化结果，建议用真实压测或线上统计替换占位：缓存命中场景平均响应耗时降低 X%、重复告警 LLM 调用次数降低 X%、RAG TopK 人工有效率提升至 X%、人工介入率下降 X%、告警平均处理时长降低 X%。当前仓库代码没有这些线上指标，不建议凭空写固定数字。

## 1. LangGraph 可编排诊断工作流

### 针对的问题

旧版逻辑是直接拉取消息，然后去 Milvus 查历史消息，有相似内容就把历史回复拼进 Prompt，再询问 LLM。这种链路适合 Demo，但不适合真实告警处置：

- 无法表达缓存命中直接返回、校验失败重试、人工拒绝重分析等分支。
- 每一步都耦合在一起，排查问题时不知道是检索、工具调用还是 LLM 生成出错。
- 缺少节点级状态，无法恢复中断流程，也无法把人工卡片回调接回原工作流。
- 后续想加新能力时只能继续堆业务判断，维护成本会越来越高。

### 通过的方案

项目用 `src/agent_sentinel/graph/workflow.py` 中的 `DiagnosisWorkflow` 承载主流程，用 LangGraph `StateGraph` 构建节点，并从 `config/workflow.yaml` 读取节点和条件边。

当前节点包括：

- `understand`：理解告警，并执行历史案例缓存检查。
- `retrieve`：执行 Hybrid RAG 检索。
- `fetch_live_data`：拉取指标、日志、拓扑等实时数据。
- `generate_plan`：生成结构化诊断方案。
- `validate`：做规则校验和 LLM 校验。
- `human_confirm`：等待人工确认。
- `final_result`：生成最终结果。
- `feedback_learning`：收集反馈并决定是否入库。

关键路由包括：

- `cache_decision`：缓存命中并采用时从 `understand` 直达 `final_result`。
- `should_fetch`：根据告警内容判断是否需要实时数据。
- `validation_result`：校验失败回到 `generate_plan`。
- `human_decision`：人工拒绝回到 `generate_plan`，批准或超时进入最终结果。
- `feedback_learning`：最终结果后进入知识沉淀闭环。

### 为什么选这种实现

告警诊断本质是状态机，不是单轮问答。LangGraph 适合表达“节点 + 状态 + 条件边 + interrupt/resume”的流程，既保留 LLM 的推理能力，又把关键业务路径显式固定下来。相比完全自主 Agent，它更可控；相比手写 `if/else`，它更清晰，也更方便测试。

### 为什么不选其他方式

- 不继续使用单次 Prompt：无法做局部重试、人工确认、反馈学习和节点级观测。
- 不手写流程编排：短期代码量少，但流程变复杂后容易变成不可维护的嵌套判断。
- 不完全交给 LLM 自主规划：告警处置涉及风险控制，不能让模型自由决定是否跳过校验或执行危险建议。

### 实现优势

- 可观测：每个节点完成后都能发进度。
- 可恢复：通过 `workflow_thread_id` 和 checkpointer 支持状态恢复。
- 可扩展：新增 Prometheus、ELK、CMDB、工单等能力时可以作为节点接入。
- 可控：流程分支由配置和规则控制，而不是完全依赖模型自由发挥。

## 2. 多 Agent 职责拆分与状态协同

### 针对的问题

旧版把“理解告警、找历史、组织 Prompt、生成答案”放在同一条链路里，导致模型职责混杂：

- Prompt 越写越长，难以维护。
- 检索结果、实时数据和最终方案之间缺少统一状态承载。
- 无法清楚判断每个环节贡献了什么证据。
- 后续接入更多工具时，主逻辑会变得臃肿。

### 通过的方案

项目将诊断拆成多个专职 Agent 节点，每个节点只负责一种能力：

- Understand Agent：生成告警摘要，并做历史案例缓存检查。
- Retrieve Agent：构造 `RagFilters`，调用统一 retriever，返回 Prompt 上下文。
- Tool Fetch Agent：并发获取指标、日志、拓扑。
- Plan Generate Agent：基于告警摘要、RAG、工具数据生成结构化方案。
- Validate Agent：校验方案是否安全、是否可执行。
- Human Confirm Agent：在关键节点引入人工确认。
- Final Result Agent：组装最终回复。
- Feedback Learning Agent：把有效结果沉淀为历史案例。

这些节点通过 `DiagnosisState` 协同，状态中包含：

- `raw_alert`
- `alert_summary`
- `retrieved_docs`
- `live_data`
- `recommended_plan`
- `evidence`
- `validation_result`
- `human_decision`
- `final_text`
- `messages`

### 为什么选这种实现

多 Agent 的核心不是“多几个模型调用”，而是把复杂流程拆成职责清晰、输入输出明确的模块。这样每个节点都能独立测试、独立调优，也便于后续替换某个节点的实现，例如把 Mock 工具换成真实监控系统，把普通检索换成 reranker。

### 为什么不选其他方式

- 不把所有能力塞进一个大 Prompt：上下文不可控，错误定位困难，任何小改动都可能影响整体输出。
- 不把所有逻辑写在一个服务函数里：扩展工具或调整流程时容易牵一发动全身。
- 不让每个 Agent 自己维护私有状态：跨节点证据难以汇总，也不利于最终入库和复盘。

### 实现优势

- 模块边界清楚：节点输入输出可追踪。
- 证据链可沉淀：各节点通过 `append_evidence` 累积判断依据。
- 调优成本低：可以单独优化检索、生成、校验或反馈节点。
- 面试表达强：这是“检索-推理-执行-校验-记忆”的完整 Agent 工程化闭环。

## 3. 静态文档索引与元数据抽取

### 针对的问题

旧版只依赖历史消息，缺少稳定的标准知识来源。历史消息往往包含临时讨论、口语表达和过时方案，不适合作为唯一依据。真实告警诊断需要 SOP、Runbook、FAQ、架构说明和故障手册等稳定知识。

### 通过的方案

项目在 `src/agent_sentinel/rag/static_ingest.py` 中实现静态文档索引流程，支持 Markdown 和 JSONL 两种输入：

1. 读取 `data/static_docs` 下的 `.md`、`.markdown`、`.jsonl` 文件。
2. 对 Markdown 使用 `MarkdownHeaderTextSplitter` 按 `#`、`##`、`###` 标题层级切片。
3. 解析 frontmatter，保留 `id`、`title`、`doc_type`、`service`、`component`、`tags`、`version`、`source_uri` 等字段。
4. 自动抽取增强元数据：
   - `doc_id`：文档标识。
   - `chunk_index`：切片序号。
   - `section`：标题层级拼接出的章节路径。
   - `alert_category`：基于一级标题识别 MQ、JVM、MySQL、Redis、K8s 等类别。
   - `severity_level`：基于“核心业务致命故障”“高危”“严重”“飙升”等词识别 P0/P1/P2。
   - `error_code`：抽取 429、500、503、504、OutOfMemoryError、Connection pool exhausted 等错误码或错误模式。
   - `keywords`：从加粗文本、故障定义、根因、解决方案、排查步骤等内容抽取关键词。
   - `source`、`file_path`、`last_updated`：用于追溯来源。
5. 使用 EmbeddingClient 对每个切片向量化。
6. 通过 `StaticDocIngestor` 按 batch upsert 到 Milvus。

### 为什么选这种实现

按 Markdown 标题切片比固定字符长度切片更符合运维文档结构。故障手册通常天然按“故障类型 -> 现象 -> 根因 -> 处理方案”组织，标题层级能保留语义边界。再叠加元数据，检索时不仅能靠向量相似度，还能按服务、类别、严重级别和来源做过滤或展示。

### 为什么不选其他方式

- 不使用整篇文档入库：粒度太粗，召回后会塞入大量无关内容，浪费 Prompt token。
- 不使用固定长度切片：可能把现象和解决方案切断，破坏排障语义。
- 不只存纯文本：后续无法按服务、类别、严重级别过滤，也不利于解释召回来源。
- 不只依赖人工维护 metadata：成本高，容易漏填，自动抽取能保证最低可用质量。

### 实现优势

- 召回更精准：切片粒度贴近运维文档章节。
- 可解释性更强：结果能展示章节、类别、严重级别和来源。
- 后续可扩展：metadata 可继续用于 reranker、过滤器、评估集和召回调试。
- 入库效率可控：批量 embedding 和 batch upsert 适合批量导入故障手册。

## 4. 双路 Hybrid RAG 检索与 MMR 去冗余

### 针对的问题

旧版只从 Milvus 里查历史消息，相似度高不代表对当前告警有帮助。常见问题包括：

- 多条历史消息内容高度重复。
- 历史回复可能缺少标准处理步骤。
- 最近发生的成功案例有价值，但也不能完全替代 SOP。
- Prompt 上下文空间有限，不能无脑塞 TopK。

### 通过的方案

项目在 `src/agent_sentinel/rag/hybrid_retriever.py` 中实现 Hybrid RAG：

- `StaticDocRetriever` 检索 `aiops_static_docs`，提供稳定知识。
- `MessageHistoryRetriever` 检索 `aiops_message_history`，提供历史成功案例。
- 两路 retriever 通过 `asyncio.gather` 并发召回。
- 静态文档检索按 `service == 当前服务 or service == "global"` 过滤。
- 历史案例检索固定过滤 `doc_type == "alert_case"`，并默认只看最近 30 天。
- 静态文档默认权重 `0.55`，历史案例默认权重 `0.45`。
- 7 天内历史案例做 `1.2` 近期加权，30 天外降权到 `0.8`。
- 合并后按 `source_type + id` 去重。
- 最后用 MMR 选择最终 TopK，在相关性和多样性之间取平衡。

MMR 公式：

```text
mmr_score = lambda * relevance - (1 - lambda) * diversity_penalty
```

当前 `RAG_MMR_LAMBDA=0.55`，表示略偏相关性，同时保留多样性约束。

### 为什么选这种实现

静态知识和历史案例解决的是不同问题。静态知识回答“标准上应该怎么处理”，历史案例回答“最近类似问题实际怎么处理”。双路检索能保留两类知识的独立治理能力，再通过权重和 MMR 统一选择进入 Prompt 的上下文。

### 为什么不选其他方式

- 不把静态文档和历史消息混在一个 collection：生命周期、可信度、过滤逻辑、权重策略都不同，混存后难治理。
- 不只用普通 TopK：容易被重复内容占满上下文。
- 不直接上复杂 reranker：reranker 可能效果更好，但会增加模型调用成本和延迟；当前阶段 MMR 是低成本、可解释的折中。
- 不只用关键词检索：中文告警表达差异大，语义向量召回更适合处理同义表达。

### 实现优势

- 上下文质量更高：标准预案和历史经验互补。
- Prompt 更干净：MMR 避免重复结果堆叠。
- 成本更可控：先用轻量策略筛选，再进入 LLM。
- 降级更稳：单路 retriever 失败时记录日志并继续使用其他结果。

## 5. 历史成功案例缓存复用

### 针对的问题

运维告警有明显重复性。如果每次重复告警都完整执行 RAG、工具调用和 LLM 方案生成，会造成：

- 响应时间变长。
- LLM token 成本增加。
- 值班人员反复看相同分析。
- 历史成功经验没有被高效复用。

### 通过的方案

项目在 `understand_node` 中加入历史案例缓存逻辑：

1. 用当前告警的 `summary`、`details`、`raw_text` 构造 `alert_text`。
2. 调用 `HistoryCaseStore.search_similar_cases` 检索 Milvus 中的 `alert_case`。
3. 使用相似度阈值控制复用，默认 `RAG_CASE_CACHE_THRESHOLD=0.85`。
4. 默认取 Top2 候选案例。
5. 命中后发送飞书卡片，展示候选案例、相似度和历史方案。
6. 用户点击“采用此方案”后，直接把历史方案转成 `recommended_plan`。
7. 设置 `cache_hit=True`、`validation_result=True`、`need_human=False`，并通过 LangGraph 条件路由跳到 `final_result`。
8. 用户拒绝则继续完整诊断链路。

### 为什么选这种实现

缓存复用不能完全自动化。告警相似不代表根因相同，尤其生产环境变更频繁，所以项目采用“高置信召回 + 人工一键确认”的方式，把成本优化和风险控制结合起来。

### 为什么不选其他方式

- 不完全自动采用最高相似案例：可能把过时或不适用方案直接发给用户。
- 不每次都走完整链路：重复告警下成本和延迟都不划算。
- 不只用本地内存缓存：历史案例需要跨进程、跨部署、长期沉淀，Milvus 更适合语义相似复用。
- 不按纯文本 hash 缓存：告警表达稍有变化就命不中，语义向量更适合相似故障。

### 实现优势

- 重复告警更快：确认采用后跳过后续重流程。
- 成本更低：减少重复 LLM 生成和工具调用。
- 风险可控：由值班人员决定是否采用。
- 体验更好：飞书卡片直接展示相似度和历史方案。

## 6. 反馈学习与长期记忆闭环

### 针对的问题

如果 AI 的每次输出都自动入库，错误方案会污染历史案例库；如果完全不入库，系统又无法从真实处置中积累经验。需要一种可控的知识沉淀机制。

### 通过的方案

项目在 `feedback_learning_node` 中实现最终反馈学习：

- 最终结果发送后，飞书卡片询问“当前回复是否有效”。
- 用户选择“有效，存入知识库”后，调用 `HistoryCaseStore.save_case_to_history`。
- 入库内容包括：
  - 原始告警。
  - 告警摘要。
  - RAG 检索结果。
  - 实时数据。
  - 推荐方案。
  - 证据链。
  - 校验结果。
  - 人工决策。
  - 最终回复。
  - 完整工作流日志。
- 用户选择“无效，不存储”时，本次结果不会进入历史案例库。
- 入库时统一设置 `doc_type="alert_case"`，供后续缓存复用和历史案例检索过滤。
- 对 Milvus 的 VARCHAR 字段做 UTF-8 字节级截断，避免中文超长导致 upsert 失败。

### 为什么选这种实现

长期记忆的关键不是“存得多”，而是“存得准”。告警处置中，人工确认是非常有价值的弱监督信号。只存有效案例，可以让历史案例库逐步变成高质量经验库，而不是 AI 输出垃圾箱。

### 为什么不选其他方式

- 不自动存所有回答：错误答案会被后续 RAG 召回，形成负反馈循环。
- 不只存最终文本：缺少 RAG、工具数据和证据链，后续复盘价值低。
- 不只存数据库行、不存向量：无法支持语义相似检索。
- 不完全依赖人工手写案例：质量高但成本太大，反馈卡片能把沉淀成本降到一次点击。

### 实现优势

- 形成数据闭环：诊断结果反哺历史案例库。
- 降低污染风险：无效结果不入库。
- 可复盘：metadata 保留完整上下文。
- 可持续优化：后续可基于有效案例构建评估集或调优 Prompt。

## 7. LLM 调用可靠性与方案安全校验

### 针对的问题

LLM 在生产系统中是不稳定外部依赖，可能超时、失败、输出格式错误，也可能生成危险操作建议。告警助手如果直接把这些建议发到群里，会有明显风险。

### 通过的方案

项目做了两层保障。

第一层是统一 LLM 调用封装，位于 `src/agent_sentinel/llm/executor.py`：

- 支持多个模型，主模型失败后切换备用模型。
- 支持 `asyncio.timeout`。
- 支持 tenacity 指数退避重试。
- 支持 Mock 模式，便于本地演示和自动化测试。
- 记录模型、耗时、Prompt 长度和响应长度。

第二层是输出约束与安全校验：

- `generate_plan_node` 使用 `PydanticOutputParser`，要求输出 `recommended_plan`、`evidence`、`need_human`。
- `validate_plan_node` 先用规则拦截危险关键词，包括 `rm -rf`、`drop table`、`shutdown`、`reboot`、`kubectl delete`、`delete from`。
- 再调用 LLM 做二次校验，输出 `PASS` 或 `FAIL`。
- 校验失败时回到 `generate_plan` 重新生成，超过逻辑上限后继续，避免无限循环。

### 为什么选这种实现

LLM 输出需要被当作“不可信输入”处理。结构化解析解决格式问题，规则校验解决确定性高危命令，LLM 二次校验补充语义层判断。多模型、超时和重试则保证外部模型服务不稳定时主流程仍尽量可用。

### 为什么不选其他方式

- 不在业务节点里直接调模型：每个节点都要重复处理超时、重试和降级，行为不一致。
- 不只靠 Prompt 约束模型：Prompt 无法保证永远不输出危险内容。
- 不只做 LLM 校验：模型校验本身也可能漏判，确定性危险词应先用规则拦截。
- 不要求完全人工审核所有输出：会降低自动化效率，应该只在关键节点和高风险方案中介入。

### 实现优势

- 输出更稳定：结构化结果方便展示、校验和入库。
- 风险更可控：危险操作不会直接进入最终建议。
- 可测试性更好：Mock LLM 支持本地和 CI 测试。
- 可运维性更强：统一日志便于定位模型调用问题。

## 8. 异步工具调用、飞书交互与可观测体验

### 针对的问题

真实告警诊断需要结合指标、日志、拓扑等外部数据。如果串行调用，整体耗时会被多个系统累加。同时，飞书群告警场景对用户体验要求很高，如果每个节点都发送一条新消息，会刷屏；如果完全不发进度，用户又会以为系统卡死。

### 通过的方案

项目从执行效率和交互体验两方面优化。

执行效率：

- `fetch_all_live_data` 使用 `asyncio.gather` 并发执行 `get_metrics`、`query_logs`、`get_topology`。
- 每个工具都设置 `asyncio.timeout(5)` 和最多 2 次重试。
- 目前工具是 Mock 实现，但接口边界已经稳定，后续可替换为 Prometheus、ELK、CMDB、K8s、工单系统等真实数据源。

飞书交互：

- 普通工作流通过 `_send_progress` 在节点完成后发送进度。
- 交互式话题流程使用 `InteractiveTopicWorkflow`，在原消息话题下创建单张卡片。
- 卡片持续更新节点状态，包含缓存检查、RAG 检索、工具调用、总结等步骤。
- 每个节点支持“同意”“拒绝”，拒绝后可重试，最多重试 2 次后自动跳过。
- 超时未操作时自动继续，避免工作流长时间阻塞。
- 最终结果后提供有效/无效反馈按钮，衔接历史案例入库。

### 为什么选这种实现

告警场景需要“快”和“可见”。异步并发能降低工具等待时间，单卡片更新能避免群聊刷屏，同时保留人工介入能力。相比完全后台执行，进度卡片更适合值班协作场景。

### 为什么不选其他方式

- 不串行调用工具：延迟会线性叠加。
- 不让外部工具失败阻断全部流程：工具是增强信息，不应该成为单点故障。
- 不每步发送新卡片：群聊会被刷屏，用户难以追踪当前状态。
- 不无限等待人工确认：值班人员可能没及时操作，超时继续能保障流程推进。

### 实现优势

- 响应更快：工具并发减少等待时间。
- 用户体验更好：同一张卡片展示完整进度。
- 可扩展性强：工具接口可以平滑替换成真实系统。
- 可控性更高：人工可以拒绝节点结果并触发重试。

## 面试展开顺序

可以按下面的顺序讲，逻辑会比较顺：

1. 先讲旧版问题：只检索历史消息并拼 Prompt，缺少标准知识、流程控制、校验和反馈闭环。
2. 讲 workflow：用 LangGraph 把线性链路拆成可恢复的状态机。
3. 讲 multi-agent：每个节点承担一个明确职责，用统一状态传递证据。
4. 讲 RAG 索引：Markdown 标题切片 + 元数据抽取 + Milvus 向量入库。
5. 讲 RAG 检索：静态文档 + 历史案例双路召回，权重、时间窗口、MMR 控噪。
6. 讲成本优化：历史成功案例缓存命中后由人工确认并跳过重流程。
7. 讲记忆闭环：有效反馈才入库，避免知识库污染。
8. 讲稳定性：LLM 降级、超时、重试、结构化解析、安全校验、并发工具调用和飞书单卡片进度。

## 可补充的量化指标口径

如果后续要把这段写得更像正式简历成果，可以补充这些真实指标：

- 缓存命中率：历史成功案例缓存命中的告警占比。
- 缓存采用率：命中后被人工选择采用的比例。
- 重复告警成本：缓存命中前后平均 LLM 调用次数和 token 消耗。
- 端到端耗时：完整链路、缓存命中链路、工具并发前后的平均耗时。
- RAG 有效率：TopK 检索结果被人工认为有帮助的比例。
- 人工介入率：需要人工重分析或拒绝方案的比例。
- 安全拦截数：危险命令或不合规方案被校验节点拦截的次数。
- 知识库质量：反馈入库案例后续再次被采用的比例。
