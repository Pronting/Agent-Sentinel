# AI 告警助手项目简历亮点提炼

## 可直接写进简历的版本

主要工作：参与自研 AI 智能告警助手（Agent Sentinel / Seatalk-bot）的优化迭代，将原先“拉取消息 -> Milvus 相似历史消息检索 -> 拼接历史回复调用 LLM”的线性链路，升级为可编排、可校验、可反馈学习的多 Agent 告警诊断系统，兼顾回答准确性、处理成本和运维可控性。

- 针对单次 LLM 分析链路缺少状态编排、诊断过程不可观测、失败后难以重试的问题，通过 LangGraph 将告警理解、历史缓存命中、混合 RAG、实时数据获取、方案生成、安全校验、人工确认、反馈学习拆分为可配置节点，并基于 YAML 条件路由控制缓存命中直达、校验失败重生成、人工拒绝重分析等分支，实现告警诊断流程从单轮问答升级为可追踪、可恢复、可干预的多阶段工作流。

- 针对仅依赖历史相似消息导致上下文噪声高、标准 SOP 覆盖不足、TopK 结果重复的问题，通过构建“静态文档库 + 历史成功案例库”的双路 Milvus RAG 架构，引入服务过滤、时间窗口、来源加权、近期案例加权与 MMR 去冗余策略，实现 Prompt 上下文从单一历史回复扩展为“标准预案 + 近期实战案例”的高相关、多样化证据链。

- 针对重复告警反复调用 LLM、历史案例复用缺少人工把关、无效回答容易污染知识库的问题，通过在告警理解阶段增加相似案例缓存检索与飞书卡片确认，高置信历史案例可一键采用并跳过后续诊断节点；同时在最终结果后增加“有效/无效”反馈学习卡片，仅将人工确认有效的告警、RAG 结果、工具数据、推荐方案和证据链写入 Milvus，实现重复告警降本提速与知识库正向自进化。

- 针对 LLM 输出不稳定、自动化建议存在高危操作风险、诊断链路容易被单点工具拖慢的问题，通过统一 LLMExecutor 封装多模型降级、超时、指数退避重试与 Mock 模式，结合 Pydantic 结构化输出解析、危险命令规则校验 + LLM 二次校验，以及指标/日志/拓扑工具并发获取，实现诊断方案生成的稳定性、安全性和端到端处理效率提升。

> 注：如果简历必须写量化结果，建议用真实压测或线上统计替换为“缓存命中场景平均耗时降低 X%”“重复告警 LLM 调用次数降低 X%”“人工采纳率提升至 X%”“RAG 召回人工有效率提升至 X%”。当前代码中没有可靠的线上指标，不建议直接写“75% 到 95%”这类数字。

## 亮点一：LangGraph 多 Agent 告警诊断工作流

### 针对的问题

旧链路本质是一次性调用：拿到消息后检索历史相似消息，把历史回复塞进 Prompt，再询问 LLM。这种方式有几个明显短板：

- 流程是线性的，无法表达“缓存命中直接返回”“校验失败重新生成”“人工拒绝后重分析”等真实运维分支。
- 中间过程不可见，用户只能等待最终结果，无法知道系统卡在理解、检索、工具调用还是 LLM 生成。
- 失败处理粗糙，某个步骤失败后很难只重试当前节点。
- 诊断证据散落在 Prompt 和回复里，后续复盘、入库、评估都不方便。

### 采用的方案

项目通过 `src/agent_sentinel/graph/workflow.py` 定义 `DiagnosisWorkflow`，用 LangGraph `StateGraph` 承载完整诊断状态，并从 `config/workflow.yaml` 动态读取节点和条件边。

当前主流程包含：

- `understand`：告警理解，并尝试历史成功案例缓存命中。
- `retrieve`：执行混合 RAG 检索。
- `fetch_live_data`：获取指标、日志、拓扑等实时数据。
- `generate_plan`：生成结构化诊断方案和证据链。
- `validate`：执行规则校验和 LLM 校验。
- `human_confirm`：等待人工确认。
- `final_result`：组装并发送最终结果。
- `feedback_learning`：根据人工反馈决定是否入库。

条件路由则把业务策略显式化：

- `understand -> final_result`：历史缓存命中并被采用时，直接复用历史方案。
- `understand -> retrieve`：缓存未命中或被拒绝时，进入完整诊断。
- `retrieve -> fetch_live_data / generate_plan`：根据告警关键词判断是否需要实时数据。
- `validate -> generate_plan`：校验失败时回到方案生成。
- `human_confirm -> generate_plan / final_result`：人工拒绝则重生成，批准或超时则继续。
- `final_result -> feedback_learning`：最终结果后进入反馈闭环。

### 为什么这样实现

告警诊断不是简单问答，而是一个天然带状态、带分支、带人工介入的流程。LangGraph 的优势在于能把这些流程显式表达成状态机，而不是散落在业务代码里的 `if/else`。同时项目把节点写进 `workflow.yaml`，后续增加节点或调整路由时，不需要重写主控制逻辑。

### 其他方案的劣势

- 继续使用单次 Prompt：开发快，但无法稳定表达校验、人工确认、反馈学习等闭环能力。
- 手写流程编排：短期可控，但节点一多就容易形成复杂嵌套逻辑，后续维护和测试成本高。
- 全部交给 Agent 自主规划：灵活性强，但在告警处置场景中可控性不足，尤其不适合直接生成执行建议。

### 这样实现的优势

- 流程可观测：每个节点都能发送进度消息，用户知道当前执行阶段。
- 流程可恢复：使用 `workflow_thread_id` 和 checkpointer 维护线程状态，配合 `resume` 支持卡片回调继续执行。
- 风险可控：关键节点之间有显式校验和人工确认。
- 易扩展：后续接入真实 Prometheus、ELK、CMDB、工单系统时，可以作为新节点插入。

## 亮点二：静态文档 + 历史案例的双路 Hybrid RAG

### 针对的问题

旧实现只查 Milvus 中的历史消息，如果有相似历史消息，就把历史回复作为提示词。这会带来三个问题：

- 历史消息质量不稳定，可能混入闲聊、错误判断、过时方案。
- 只依赖历史消息，无法稳定引用 SOP、Runbook、FAQ、故障手册等标准知识。
- TopK 相似结果往往高度重复，Prompt 被相似内容占满，覆盖不到更多排障角度。

### 采用的方案

项目将 RAG 数据源拆成两类：

- `StaticDocRetriever`：检索 `aiops_static_docs`，用于召回 SOP、Runbook、FAQ、故障预案等稳定知识。
- `MessageHistoryRetriever`：检索 `aiops_message_history`，用于召回历史成功告警案例。

`HybridRetriever` 并发调用多个 retriever，之后做统一合并：

1. 生成 query embedding。
2. 并发召回静态文档与历史案例。
3. 对静态文档按 `service == 当前服务 or global` 过滤。
4. 对历史案例按 `doc_type == "alert_case"` 和最近 N 天过滤。
5. 按来源设置权重，静态文档默认 `0.55`，历史案例默认 `0.45`。
6. 对 7 天内历史案例做近期加权。
7. 去重后使用 MMR 在相关性和多样性之间取平衡。
8. 输出最终 TopK 文档进入 Prompt。

相关实现主要在：

- `src/agent_sentinel/rag/hybrid_retriever.py`
- `src/agent_sentinel/rag/static_doc_retriever.py`
- `src/agent_sentinel/rag/message_history_retriever.py`
- `src/agent_sentinel/rag/mmr.py`

### 为什么这样实现

静态文档和历史案例的价值不同。静态文档可信度更高，适合提供标准操作路径；历史案例贴近当前业务现场，适合提供近期处置经验。把两者拆成不同 collection 和 retriever，可以分别设置过滤条件、权重、生命周期和召回策略，避免所有内容混在一起后难以治理。

MMR 的引入则解决了 TopK 只追求相似度的问题。对告警诊断来说，最相似的一批文档经常是重复描述同一个现象，而真正有价值的是覆盖“现象、原因、验证、处置、回滚”等多个角度。

### 其他方案的劣势

- 单 collection 混存：实现简单，但无法对静态知识和动态案例做差异化权重、过滤和生命周期管理。
- 只按向量相似度 TopK：容易召回多条重复内容，浪费 Prompt token。
- 只做关键词检索：对表达差异、别名、中文运维描述的兼容性较差。
- 引入复杂 reranker：效果可能更好，但会增加一次模型调用成本和延迟，当前阶段 MMR 是成本更低的折中。

### 这样实现的优势

- 准确性更稳：标准 SOP 和历史案例互补，减少只看历史回复造成的误导。
- 成本更可控：先通过权重和 MMR 做轻量筛选，减少进入 Prompt 的冗余上下文。
- 可治理性更强：静态文档、历史案例可以独立更新、清洗和评估。
- 降级友好：Milvus 未配置时会回退 Mock retriever，RAG 单路失败也不会阻断主流程。

## 亮点三：历史案例缓存复用与反馈学习闭环

### 针对的问题

告警系统中大量问题是重复出现的。如果每次都完整调用 LLM、RAG 和工具，不仅成本高，也会增加响应时间。同时，历史方案是否还能复用，需要人工确认；否则旧方案可能因为环境变化而失效。另一个问题是知识库污染：如果把所有 AI 结果都写回 Milvus，错误方案会被后续反复召回。

### 采用的方案

项目在 `understand` 节点增加历史成功案例缓存检索：

- 使用当前告警的 summary、details、raw_text 构造检索文本。
- 在 `aiops_message_history` 中只搜索 `doc_type == "alert_case"` 的成功案例。
- 使用相似度阈值，默认 `0.85`，TopK 默认 `2`。
- 命中后通过飞书卡片展示候选案例、相似度和历史方案。
- 人工点击“采用此方案”后，直接生成 `recommended_plan`，设置 `cache_hit=True`，跳过后续 RAG、工具调用和方案生成节点。
- 人工拒绝则继续完整诊断链路。

最终结果之后，`feedback_learning` 节点发送反馈卡片：

- 点击“有效，存入知识库”后，系统将本次告警、检索结果、实时数据、推荐方案、证据链、最终文本和工作流日志写入 Milvus。
- 点击“无效，不存储”后，本次结果不会污染历史案例库。
- 写入前会对 Milvus VARCHAR 字段做 UTF-8 字节级截断，避免中文内容超长导致入库失败。

相关实现主要在：

- `src/agent_sentinel/agents/understand_agent.py`
- `src/agent_sentinel/agents/feedback_learning.py`
- `src/agent_sentinel/rag/history_cases.py`
- `src/agent_sentinel/feishu/sender.py`
- `tests/test_case_cache_feedback.py`

### 为什么这样实现

重复告警最适合走“高置信缓存 + 人工确认”的路径。它既能降低成本，又不会完全自动复用历史方案。反馈学习则把知识库更新权交给用户，保证只有被确认有效的案例进入长期记忆。

### 其他方案的劣势

- 所有命中自动复用：成本最低，但一旦历史案例过时，容易给出错误处置建议。
- 每次都完整调用 LLM：准确性可能更好，但重复告警成本高、响应慢。
- 所有结果自动入库：短期数据增长快，但错误结果会污染后续召回。
- 只记录最终答案：复盘信息不足，后续难以判断为什么当时这么回答。

### 这样实现的优势

- 重复告警低成本：命中并确认后可跳过后续重流程。
- 知识库质量可控：只存人工确认有效的案例。
- 复盘信息完整：metadata 中保存 RAG、工具数据、方案、证据、最终文本和流程日志。
- 对中文内容友好：入库前按 UTF-8 字节截断，规避 Milvus 字段长度限制。

## 亮点四：LLM 调用稳定性、方案安全校验与交互体验优化

### 针对的问题

告警诊断中的 LLM 输出有不确定性，可能超时、格式不合法，甚至生成危险操作建议。与此同时，指标、日志、拓扑等工具调用如果串行执行，会拖慢整体诊断；飞书群内如果每个阶段都发新消息，也容易刷屏。

### 采用的方案

项目从三个层面做了稳定性和体验优化。

第一层是 LLM 调用封装。`LLMExecutor` 支持：

- 多模型列表，主模型失败后自动切换备用模型。
- `asyncio.timeout` 控制单次调用时长。
- tenacity 指数退避重试。
- Mock 模式，方便本地开发和测试。
- 统一日志记录调用耗时、Prompt 长度和响应长度。

第二层是输出结构化和安全校验：

- `generate_plan` 使用 `PydanticOutputParser` 要求 LLM 输出 `recommended_plan`、`evidence`、`need_human`。
- `validate` 先用规则拦截 `rm -rf`、`drop table`、`kubectl delete` 等危险关键词，再调用 LLM 做二次校验。
- 校验失败时通过 LangGraph 回到 `generate_plan` 重新生成，避免不安全方案直接发送给用户。

第三层是实时数据和飞书交互：

- `fetch_live_data` 使用 `asyncio.gather` 并发获取指标、日志、拓扑，避免串行等待。
- 普通诊断流程会发送节点进度消息，交互式话题流程则使用单张飞书卡片持续 PATCH 更新当前节点状态。
- 每个节点可同意、拒绝、超时自动继续；拒绝后最多重试 2 次，避免无限循环。

相关实现主要在：

- `src/agent_sentinel/llm/executor.py`
- `src/agent_sentinel/agents/generate_plan.py`
- `src/agent_sentinel/agents/validate_plan.py`
- `src/agent_sentinel/tools/mock_tools.py`
- `src/agent_sentinel/interactive_topic/workflow.py`

### 为什么这样实现

告警助手不是普通聊天机器人，它输出的是运维处置建议。稳定性和安全性比“回答得像人”更重要。因此项目把 LLM 当成一个可能失败、需要约束的外部依赖来封装，而不是在业务节点里直接调用模型。

### 其他方案的劣势

- 业务代码直接调用 LLM：每个节点都要重复写超时、重试、降级，且行为不一致。
- 只靠 Prompt 要求安全：无法可靠拦截高危命令。
- 工具串行调用：实现简单，但端到端耗时会被多个外部系统累加。
- 每一步都发新消息：实现简单，但群聊可读性差，用户难以聚焦当前状态。

### 这样实现的优势

- LLM 可靠性更高：失败可重试、可降级、可观测。
- 输出可解析：结构化结果方便后续校验、展示、入库和测试。
- 安全边界更清晰：危险操作先规则拦截，再模型复核。
- 交互体验更好：用户能看到进度，也能在关键节点介入。

## 面试展开建议

如果面试官追问“你具体做了什么”，可以按这个顺序回答：

1. 先讲旧链路问题：只检索历史消息再拼 Prompt，缺少标准知识、流程控制、校验和反馈闭环。
2. 再讲架构升级：LangGraph 节点化，把诊断拆成理解、检索、工具、生成、校验、人工确认、反馈学习。
3. 然后讲 RAG 优化：静态 SOP 和历史案例分库，权重融合，MMR 去重，避免重复历史消息占满上下文。
4. 最后讲成本和闭环：相似案例缓存可人工采用并跳过后续节点，只有有效反馈才入库。

可准备的量化指标：

- 缓存命中后平均响应时间：完整诊断耗时 vs 采用历史案例耗时。
- LLM 调用次数：完整流程调用次数 vs 缓存命中调用次数。
- RAG 召回质量：人工采纳率、TopK 有效率、重复召回比例。
- 告警处理效率：人工介入前平均等待时间、重复告警处理耗时。
